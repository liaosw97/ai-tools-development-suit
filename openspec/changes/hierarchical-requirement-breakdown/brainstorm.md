# Brainstorm: hierarchical-requirement-breakdown

> 深度探索记录 — 记录需求探索过程和关键决策

## 需求描述

为 SDD 工作流增加**需求分层拆分（Hierarchical Requirement Breakdown）**能力，实现渐进式探索和独立功能验证：

1. **需求探索阶段**：先将需求进行分层拆分，再逐层探索
   - L1：功能模块列表（如：后台管理 → 人员管理、单位管理...）
   - L2：功能单元列表（如：人员管理 → 列表页、新增、查看、修改...）
   - L3：具体功能点（对每个功能单元进行详细询问）

2. **计划阶段**：按拆分的功能单元生成任务，确保功能间最小依赖

3. **代码实施阶段**：按拆分的功能单元独立实现，方便快速调试验证

4. **目录冲突检测**：遇到功能相似的目录时，必须询问用户确认操作哪个，不能自作主张

## 方案探索

### 方案 A: 轻量增强（已选择）

在现有 SDD 流程中嵌入拆分逻辑，不改变制品结构，仅增强交互模式。

- **优点:**
  - 改动范围小，风险低
  - 与现有 SDD 流程兼容
  - 不影响不启用拆分模式的用户
- **缺点:**
  - 功能树信息分散在 brainstorm.md 中，plan 阶段需解析

### 方案 B: 独立制品

引入新制品 `breakdown.md`，专门存储功能拆分树。

- **优点:**
  - 职责清晰，功能树独立维护
  - 可单独审查和迭代
- **缺点:**
  - 增加制品复杂度
  - 用户需理解新制品的作用

### 方案 C: 深度集成

将拆分能力作为 SDD 核心能力，重构 proposal/spec/tasks 的组织方式。

- **优点:**
  - 结构化程度高，适合大型项目
- **缺点:**
  - 改动范围大，影响现有用户习惯
  - 与"可选增强模式"的设计目标冲突

### 方案比较

选择方案 A，理由：
1. 符合"可选增强模式"的定位
2. 改动范围可控，风险低
3. 用户无需学习新制品
4. 可在验证效果后逐步演进到方案 B

## 关键决策

### 决策 1: 影响范围

- **选择:** 三个阶段都需要修改（sdd-brainstorm、sdd-plan、sdd-code）
- **理由:** 拆分能力贯穿需求探索、计划生成、代码实施全流程
- **被否决的替代:** 仅修改 brainstorm 阶段 — 无法实现"按功能单元独立实现"的目标

### 决策 2: 追问时机

- **选择:** brainstorm 阶段即时触发追问
- **理由:** 拆分出功能单元后立即追问，确保在追问结果基础上继续拆分下一层，信息连贯
- **被否决的替代:** 拆完所有层后统一追问 — 可能导致上下文断层

### 决策 3: 依赖处理方式

- **选择:** 默认独立 + 异常提示
- **理由:** 符合"功能间最小依赖"的设计目标，AI 检测到潜在依赖时询问用户确认
- **被否决的替代:** 自动分析依赖排序 — 可能误判依赖关系；用户标注依赖 — 增加用户负担
- **可验证标准:** 依赖检测触发条件见"依赖检测规则"节，检测到依赖时必须输出提示并询问用户

### 决策 4: 目录冲突检测范围

- **选择:** brainstorm 和 code 阶段都需要
- **理由:** brainstorm 阶段引用已有功能时需确认；code 阶段创建文件时需确认目标目录
- **被否决的替代:** 仅在 code 阶段检测 — brainstorm 阶段可能错误引用已有模块

### 决策 5: 拆分层数控制

- **选择:** 用户可干预
- **理由:** AI 建议是否继续拆分，用户决定停止或继续，灵活性高
- **被否决的替代:** 固定三层 — 无法适应不同复杂度的需求；动态判断 — 可能与用户预期不符
- **可验证标准:** 当功能单元包含超过 3 个独立操作（可独立触发和验证的用户交互）时，AI 建议继续拆分

### 决策 6: 启用模式

- **选择:** 可选增强模式
- **理由:** 简单需求可跳过拆分，复杂需求由用户或 AI 判断是否启用
- **被否决的替代:** 默认行为 — 对简单需求增加不必要开销

### 决策 7: 触发方式

- **选择:** 参数和自然语言都支持
- **理由:** 显式参数适合命令行用户；自然语言适合交互式对话
- **被否决的替代:** 仅参数触发 — 降低可发现性

### 决策 8: 产出组织方式

- **选择:** 扁平目录 + spec 内嵌套
- **理由:** `specs/<domain>/spec.md` 内按功能单元分节，每个节有独立场景，保持目录结构简洁
- **被否决的替代:** 嵌套目录结构 — 增加文件系统复杂度；保持扁平结构 — 无法体现功能层级

### 决策 9: 代码实施策略

- **选择:** 按功能单元顺序实现，逐个验证
- **理由:** 每次实现一个功能单元，完成后运行测试验证，再进入下一个，确保独立验证
- **被否决的替代:** 并行实现 — 增加协调复杂度；单会话内分步 — 无法保证独立验证

## 约束识别

### 技术约束

- 需解析 brainstorm.md 中的功能树结构（Markdown 格式）
- 需检测项目目录结构以识别冲突
- 不改变现有制品依赖链

### 团队约束

- 需更新 SDD 文档说明拆分模式用法
- 需保持与现有 SDD 工作流的兼容性

## 功能拆分设计

### 整体架构

```
需求触发
    ↓
sdd-brainstorm (拆分模式)
    ├─ 交互式拆分：L1 → L2 → L3
    ├─ 每层即时追问
    └─ 产出：brainstorm.md (含功能树节)
    ↓
sdd-plan
    ├─ 读取功能树
    ├─ 按叶子节点顺序生成任务
    ├─ 自动检测依赖风险并提示
    └─ 产出：plan.md (按功能单元分批)
    ↓
sdd-code
    ├─ 按功能单元选择批次
    ├─ 逐个实现并验证
    └─ 遇相似目录时询问确认
```

### sdd-brainstorm 改动

**新增前置逻辑：拆分模式检测**

检测用户输入或命令参数是否触发拆分模式：
- 参数：`--breakdown` 或 `-b`
- 自然语言：包含"拆分"、"分层"、"逐步探索"等关键词

**新增核心执行：拆分模式交互流程**

1. **L1 拆分**
   - AI 提议功能模块列表
   - 用户确认或调整
   - 输出：L1 = [模块1, 模块2, ...]

2. **逐模块 L2 拆分**
   - 对每个 L1 模块：
     a. AI 提议该模块的功能单元列表
     b. 用户确认或调整
     c. 即时追问：对每个功能单元追问细节
     d. 输出：L2[模块] = [单元1, 单元2, ...]

3. **L3 拆分（可选）**
   - AI 判断是否需要继续拆分
   - 询问用户：是否继续拆分该单元？
   - 用户选择：继续拆分 / 停止拆分 / 跳过此单元
   - 即时追问：对每个功能点追问细节

4. **目录冲突检测**
   - 拆分过程中如发现相似目录，暂停并询问用户

5. **产出功能树**
   - 写入 brainstorm.md 的 "## 功能拆分" 节

**brainstorm.md 功能树格式**

```markdown
## 功能拆分

> 拆分模式启用时间：YYYY-MM-DD HH:MM

### 功能树

- **后台管理** (L1)
  - **人员管理** (L2)
    - 列表页 (L3) — 追问：字段、筛选、排序
    - 新增功能 (L3) — 追问：表单字段、校验规则
    - 查看功能 (L3) — 追问：展示字段
    - 修改功能 (L3) — 追问：可编辑字段、校验规则
  - **单位管理** (L2)
    - 列表页 (L3) — 追问：字段、筛选
    - 新增功能 (L3) — 追问：表单字段

### 拆分决策

- 选择 [三层拆分] 而非 [两层]：功能单元仍包含多个独立操作（见追问结果）
- 选择 [人员管理优先] 而非 [单位管理]：核心业务流程依赖（用户确认）
```

### sdd-plan 改动

**新增前置逻辑：功能树读取**

如果 brainstorm.md 包含 "## 功能拆分" 节：
1. 解析功能树结构
2. 提取叶子节点列表（可独立实现的功能点）
3. 检测叶子节点间的潜在依赖关系
4. 如有依赖风险：列出并询问用户确认顺序

**核心执行改动**

Override 指令新增：
- 每个叶子节点生成一组任务
- 任务组标注所属功能单元：`[unit:模块/单元/功能点]`
- 按叶子节点顺序排列任务组
- 功能单元间插入 checkpoint 标记

**plan.md 格式**

```markdown
## 批次 1：人员管理 - 列表页

<!-- 功能单元：后台管理/人员管理/列表页 -->
<!-- 依赖：无 -->

### 任务组 1.1

- [ ] 1.1.1 创建列表页组件 [unit:人员管理/列表页] [spec:人员管理#列表页]
  - RED: 编写列表页渲染测试
  - GREEN: 实现基础列表渲染
- [ ] 1.1.2 实现筛选功能 [unit:人员管理/列表页] [spec:人员管理#筛选]
  ...

--- checkpoint: 人员管理-列表页 完成 ---
```

**依赖检测规则**

自动检测以下依赖模式：
1. 数据依赖：功能 B 使用功能 A 创建的数据
2. API 依赖：功能 B 调用功能 A 提供的接口
3. UI 依赖：功能 B 的组件嵌入功能 A 的页面

检测到依赖时：
- 输出："[功能单元 B] 可能依赖 [功能单元 A]，建议 A 先实现"
- 询问：确认依赖关系？是否调整顺序？

### sdd-code 改动

**新增前置逻辑：功能单元选择**

如果 plan.md 包含功能单元标记：
1. 列出所有功能单元及其状态（已完成/进行中/待开始）
2. 询问用户：本次实现哪个功能单元？
3. 定位该功能单元的任务组
4. 确认任务范围

否则：沿用原有批次选择逻辑

**核心执行改动**

Override 指令新增：
- 每个功能单元完成后运行测试验证
- 仅验证该功能单元相关的测试（非全量测试）
- 验证通过后 checkpoint 确认

**目录冲突检测**

实现前扫描项目目录：
1. 发现相似功能目录时暂停
2. 输出：检测到多个可能的目标目录
   - 选项 A: src/pages/user/（现有用户页面）
   - 选项 B: src/components/user/（现有用户组件）
   - 选项 C: 新建目录
3. 询问用户：在哪个目录实现该功能？
4. 用户确认后继续

**"相似目录"判断标准：**
- 目录名称包含相同关键词（如 `user`、`personnel` 视为相似）
- 或目录功能语义相近（如 `pages/user/` 与 `views/user/` 视为相似）
- 相似度阈值：名称相似度 > 60%（基于关键词重叠计算）

**完成引导改动**

```
sdd-code 完成。

功能单元 [人员管理/列表页] 已实现并验证。

如需释放上下文，可安全 /clear。

★ 推荐下一步: /sdd-code — 继续下一功能单元 [人员管理/新增]
  ○ /sdd-review-code — 审查本功能单元代码
  △ /sdd-ship — 所有功能单元完成后归档
```

## 边界条件与异常流处理

### 用户中途取消拆分

- **场景:** 用户在 L1/L2/L3 拆分过程中选择取消
- **处理:** 保留已完成的部分功能树，标记为"不完整拆分"，询问用户：
  - 选项 A: 保存当前状态并退出（后续可继续）
  - 选项 B: 丢弃本次拆分，回到正常 brainstorm 流程

### 需求矛盾或无法拆分

- **场景:** 拆分过程中发现需求描述存在矛盾，或功能模块无法拆分为独立单元
- **处理:** 暂停拆分流程，输出矛盾点或阻塞原因，询问用户澄清需求

### 循环依赖

- **场景:** 功能单元 A 依赖 B，B 又依赖 A
- **处理:** 输出循环依赖警告，提供解决选项：
  - 选项 A: 合并 A 和 B 为同一功能单元
  - 选项 B: 引入中间层解耦
  - 选项 C: 用户手动指定顺序

### 新建目录路径冲突

- **场景:** 目录冲突检测时用户选择"新建目录"，但输入的路径与现有目录冲突
- **处理:** 输出冲突警告，提示用户选择其他路径或覆盖确认
