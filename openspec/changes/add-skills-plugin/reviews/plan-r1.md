# Plan Review — Round 1

**审查对象:** plan.md
**日期:** 2026-05-12

## 总结

plan.md 将 tasks.md 的 11 个任务组织为 3 个批次（Submodule 添加、同步脚本集成、文档更新），每个任务均包含 RED/GREEN 验证步骤。Spec 对齐完整，11 个任务全部覆盖。主要问题集中在：(1) 部分验证任务缺少明确的 RED 失败判定条件；(2) 批次一的 Task 1.2/1.3 粒度过细且 RED/GREEN 区分模糊；(3) Task 3.2 的修改内容不够精确，存在歧义。

## Issues

### [severity: major] Task 1.2 和 Task 1.3 的 RED/GREEN 步骤缺乏实际区分度

- **位置:** plan.md §批次一 / Task 1.2、Task 1.3
- **描述:** Task 1.2 和 Task 1.3 都是纯验证任务，无代码修改。Task 1.2 的 RED 步骤备注"此步骤已在 1.1 GREEN 中通过"，说明 RED 阶段实际已无失败可能。Task 1.3 同理——在 1.1 成功添加子模块后，目录非空和 README.md 存在是必然结果。这两个任务的 RED/GREEN 结构流于形式，不具备 TDD 的"先失败后通过"语义。
- **建议:** 考虑将 Task 1.2 和 Task 1.3 合并为一个验证步骤，或者在 plan 中明确标注这些是"idempotent verification"而非严格 TDD 步骤，避免混淆。

### [severity: minor] Task 1.2 的 RED 阶段缺失失败验证命令

- **位置:** plan.md §批次一 / Task 1.2
- **描述:** Task 1.2 的"运行验证失败"字段写道"此步骤已在 1.1 GREEN 中通过"，没有提供实际的失败验证命令。这与 plan 中其他任务统一使用 `echo $?` 检查退出码的模式不一致。
- **建议:** 要么补充一个有意义的失败验证命令（例如在删除子模块的假设场景下验证），要么明确标注为"前置步骤已覆盖，无需独立 RED 验证"。

### [severity: minor] Task 2.3 验证通过条件不够严格

- **位置:** plan.md §批次二 / Task 2.3
- **描述:** 运行验证通过条件为"脚本退出码为 0 或 1（非 2，2 表示全部失败）"。退出码 1 在 shell 约定中通常表示错误，将其视为通过不够精确。且未说明退出码 1 在此场景下具体代表什么（可能是"无可用 release tag"导致的跳过）。
- **建议:** 明确退出码 0 和 1 各自的含义，例如："0 = 成功同步或正确跳过（无 tag），1 = 部分问题但不影响功能，2 = 严重错误"。

### [severity: major] Task 3.2 修改内容不够精确

- **位置:** plan.md §批次三 / Task 3.2
- **描述:** GREEN 步骤要求"在三项目关系代码块后追加"一段文字，并"将'三项目关系'标题更新为'四项目关系'（或改为'子项目关系'）"。这里使用了"或"给出了两个选项，实施时会产生歧义。plan 应该给出唯一确定的目标状态，不应留有选择空间。
- **建议:** 确定一个方案（推荐"子项目关系"，更具扩展性），并在 GREEN 步骤中给出明确的替换内容，与 Task 3.1 类似使用精确的文本替换指令。

### [severity: minor] 批次依赖标注可以更精确

- **位置:** plan.md §批次二、§批次三
- **描述:** 批次二标注"依赖: 批次一完成"，批次三标注"依赖: 批次一完成（与批次二并行）"。但批次二的 Task 2.2（versions.lock）需要读取 `ai-tools/skills/` 目录中的 git hash，这依赖批次一的子模块添加。批次三的 Task 3.1/3.2 只涉及文本修改，严格来说只需要知道子模块存在即可。依赖关系整体正确但可以更细粒度地说明。
- **建议:** 当前标注已足够指导执行，无需修改。仅作为改进建议记录。

### [severity: minor] plan 缺少最终集成验证步骤

- **位置:** plan.md 全文
- **描述:** 三个批次各自有独立验证，但缺少一个跨批次的最终集成验证步骤（例如：确认 `git submodule status` 显示所有 4 个子模块、`bash scripts/sync-upstream.sh --help` 显示所有子项目、CLAUDE.md 完整性检查）。
- **建议:** 在批次三之后增加一个"最终验证"小节，包含 2-3 条端到端验证命令，确保所有变更协同工作。
