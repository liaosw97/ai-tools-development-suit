# Brainstorm Review R1

**审查对象**: `openspec/changes/sdd-cross-module-awareness/brainstorm.md`
**审查日期**: 2026-05-17
**审查人**: SDD Brainstorm Reviewer (R1)

---

## 评估

### 1. 方案完整性

**评级: 良好**

**分析:**

brainstorm 准确识别了 SDD 工作流的三个盲区（跨模块影响分析缺失、延后项捕获缺失、Review 覆盖度不足），且三个盲区均与需求描述中的根因分析形成直接对应关系。

方案 A 的实现路径覆盖了所有三个盲区，且每个盲区都有对应的修改点：

| 盲区 | 修改点 |
|------|--------|
| 跨模块影响分析缺失 | sdd-propose/SKILL.md — 后置逻辑增加扫描引导 |
| 延后项捕获缺失 | sdd-ship/SKILL.md — 归档前增加延后项提取 + backlog.md 模板 |
| Review 覆盖度不足 | sdd-review-spec reviewer prompt — 增加跨模块一致性维度 |

**不足之处**: sdd-brainstorm 被列为第 4 个修改点（启动时读取 backlog.md），但这解决的是"历史延后项在新变更中被重新考虑"的问题，属于增量改进而非三个核心盲区的直接修复。文档中没有明确区分哪些修改是核心修复、哪些是增强，建议在 proposal 阶段明确标注优先级。

此外，实现路径中列出了 5 个修改点，但对 **sdd-quick** 和 **sdd-ff** 这两个快进/快速路径 action 是否也需要同步修改没有提及。sdd-quick 会跳过 brainstorm 直接走 propose 流程，如果 propose 的修改生效了，sdd-quick 是否自动继承？如果 sdd-ff 跳过了 propose 直接生成 specs，跨模块扫描是否会丢失？这些边界场景需要在 proposal 中澄清。

### 2. 决策清晰度

**评级: 良好**

**分析:**

三个决策均有明确的结论、理由和排除理由：

- **决策 1（方案选择）**: 选择方案 A，理由充分（YAGNI、SDD 设计哲学、渐进演进），且对方案 B 和方案 C 均给出了具体的排除理由。排除理由基于实际数据（SkillCraft 4 个 mode vs ai-tools-bridge 13 个 skill 的差异），有说服力。
- **决策 2（backlog.md 定位）**: 明确为项目级可选制品，不纳入制品依赖链，不强制存在。这个定位合理，避免了引入新的强制性制品。
- **决策 3（提示策略）**: 选择结构化提问式引导，三个提问步骤清晰可操作。

**不足之处**: 决策 3 中"结构化提问式引导"的三个问题过于宽泛。第一个问题"列出项目中与本次变更相关的其他模块/模式"要求 AI 对项目结构有全局理解，但对于首次使用 SDD 的项目（没有历史 specs），AI 的判断依据是什么？决策中未说明 AI 在缺乏项目结构信息时的兜底策略。

### 3. YAGNI

**评级: 优秀**

**分析:**

这是本 brainstorm 最强的维度。

- 方案选择明确遵循 YAGNI 原则：仅发生过一次遗漏，不值得引入 config 或自动化基础设施。
- backlog.md 被设计为可选制品，不强制使用，不增加流程复杂度。
- 方案 B 和方案 C 被正确识别为过度工程化。
- 渐进演进路径明确：先做提示词增强，不够再升级到 config 驱动。

未发现任何不必要的功能扩展或过度设计。

### 4. 可测试性

**评级: 良好**

**分析:**

决策导向的结果是可验证的：

- **sdd-propose 修改**: 可通过生成一个涉及多模块的 proposal，验证是否包含跨模块影响分析段落来测试。
- **sdd-ship 修改**: 可通过创建一个包含 P1/P2 延后项的 proposal，执行 ship 后检查 backlog.md 是否被正确生成来测试。
- **sdd-review-spec 修改**: 可通过提交一个遗漏跨模块场景的 spec，验证 reviewer 是否识别出问题来测试。
- **backlog.md 模板**: 可通过 schema 验证测试确认模板结构正确。

**不足之处**: 提示词引导类修改的效果难以量化验证。brainstorm 中提到方案 A 的缺点是"依赖 AI 的分析能力，不能保证 100% 覆盖"，但没有定义"足够好"的验收标准。建议在 proposal 中定义具体的验收场景，例如："对于包含 2+ 模块的项目，propose 应能识别出至少 80% 的跨模块影响"。

## Issues

### Issue 1: sdd-quick 和 sdd-ff 快速路径的跨模块覆盖未讨论 [次要]

**描述**: 实现路径列出了 5 个修改点，但未提及 sdd-quick（快速全流程）和 sdd-ff（快进生成）这两个跳过部分 action 的快速路径。sdd-quick 会走 propose 路径所以可能自动继承，但 sdd-ff 直接从需求跳到 specs/tasks，完全跳过 propose 阶段，跨模块扫描引导可能不会触发。

**建议**: 在 proposal 中明确说明 sdd-quick 和 sdd-ff 是否需要同步修改，或者说明快速路径场景下跨模块检查由哪个环节兜底（例如 sdd-verify 或 sdd-review-spec）。

### Issue 2: 跨模块扫描在缺乏项目结构信息时的兜底策略缺失 [次要]

**描述**: 决策 3 的结构化提问依赖 AI 对项目结构的理解。对于首次使用 SDD 的项目、或 specs/ 目录为空的项目，AI 缺乏判断"哪些模块相关"的依据。当前没有兜底策略。

**建议**: 在 sdd-propose 的引导提示中增加一个条件分支：如果项目结构不明确（无 specs/、无 config.yaml），则简化为"列出变更可能影响的文件/目录范围"即可，不强求模块级分析。

### Issue 3: backlog.md 的生命周期管理未定义 [不阻塞]

**描述**: 决策 2 定义了 backlog.md 的定位（项目级可选制品），但未说明其生命周期。backlog 中的延后项何时被标记为完成？是否需要"关闭"机制？如果延后项在新变更中被实现，是否需要从 backlog 中移除？

**建议**: 这是一个可以延后到 proposal 甚至后续变更中讨论的问题。如果本变更只想做最小化实现（只写不管理），可以在 proposal 中将 backlog 的维护策略标注为 P2 延后项。

### Issue 4: 验收标准未量化 [次要]

**描述**: 方案 A 承认"依赖 AI 分析能力，不能保证 100% 覆盖"，但 brainstorm 中没有定义最低可接受的验收标准。提示词修改后如何判断"足够好"？

**建议**: 在 proposal 中为每个修改点定义至少一个具体的验收场景（acceptance scenario），使用 GIVEN/WHEN/THEN 格式描述预期行为。这同时也是 spec 可测试性的基础。

---

**结论: APPROVED**

brainstorm 质量良好，三个核心盲区的识别准确，方案选择理由充分且符合 YAGNI 原则。4 个 issues 中无 critical 级别，均为次要或不阻塞项。Issue 1 和 Issue 4 建议在 proposal 阶段解决；Issue 2 建议在 spec 阶段细化；Issue 3 可延后。批准进入 proposal 阶段。
