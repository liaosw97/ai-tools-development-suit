## Issues

### [minor] 执行顺序图与依赖声明矛盾

- **描述:** 批次 2 的 HTML 注释中明确标注"依赖：批次 1（backlog.md 模板需先存在）"，但在底部"执行顺序"图中却标注"批次 2 可与批次 1 并行"。这两处声明自相矛盾。
- **建议:** 批次 2 的 Task 2（sdd-ship 延后项提取）确实依赖 backlog.md 模板（Task 3.1），而 Task 4（spec-reviewer-prompt）是独立的。两种修复方案：1) 将 Task 4 拆到批次 1，使批次 2 可以严格串行在批次 1 之后；或 2) 修改执行顺序图，去掉"可与批次 1 并行"的标注，改为严格串行。推荐方案 2，因为任务量不大，串行更安全。

### [minor] Task 3.1 缺少 RED 阶段

- **描述:** Task 3.1（创建 backlog.md 模板）只有"步骤"和"验证"两部分，没有 RED/GREEN/VERIFY 的 TDD 结构。而其他任务（Task 1.1~1.5、Task 2.1~2.5、Task 4.1~4.5、Task 5.1~5.3）都遵循了 RED/GREEN/验证 的三段式结构。
- **建议:** 为 Task 3.1 补充 RED 阶段：验证文件不存在（`ls ai-tools-bridge/schemas/sdd/templates/backlog.md` 期望失败）。虽然这是创建新文件而非修改现有文件，RED 阶段看似多余，但保持结构一致性有助于执行者遵循统一模式。

### [minor] Task 6 全局验证缺少 RED/GREEN 结构

- **描述:** Task 6.1~6.4（全局验证）使用了"步骤"而非"RED/GREEN/验证"结构。虽然 Task 6 的性质是纯验证而非代码修改，但它仍然缺少 RED 阶段来说明验证前应该是什么状态。
- **建议:** 对于纯验证任务，可以接受当前结构。但如果严格执行 TDD 模式，建议将验证步骤拆分为 RED（执行前确认旧状态）和 GREEN（执行后确认新状态）两部分。

### [info] 部分验证命令可能匹配前置逻辑和后置逻辑

- **描述:** Task 6.1 和 Task 6.2 使用 `grep -n "^### [0-9]"` 验证步骤编号连续性，但 sdd-propose 和 sdd-ship 的 SKILL.md 都包含前置逻辑和后置逻辑两部分，两者都有 `### 1.`、`### 2.` 等编号。grep 整个文件会返回前置和后置逻辑的混合结果，可能造成混淆。
- **建议:** 将验证命令缩小范围，例如仅 grep 后置逻辑区域（从 `## 后置逻辑` 行开始到文件末尾），或使用行号范围限定。例如：`sed -n '/^## 后置逻辑/,$ p' ai-tools-bridge/skills/sdd-propose/SKILL.md | grep -n "^### [0-9]"`。这个问题在批次 1 和批次 2 的 Task 级验证命令中也存在（如 Task 1.1~1.5 的验证第 6 条），但那里因为只检查"命中"而非精确行号，实际影响较小。

### [info] Task 1.1~1.5 合并粒度偏粗

- **描述:** tasks.md 中的 Task 1 有 5 个子任务（1.1~1.5），plan 将它们合并为一个 Task 1.1~1.5 并标注预估 5 分钟。虽然内容上它们都是修改同一个文件的同一段区域，合并执行是合理的，但 5 分钟的预估处于粒度要求（2-5 分钟）的上限。
- **建议:** 当前可接受。如果执行中发现 5 分钟不够，可以在后续迭代中将 5 个子任务拆分为两组（1.1~1.2 为一组，1.3~1.5 为一组）。

### [info] plan 中引用的 spec-reviewer-prompt 文件路径缺少 skills 前缀说明

- **描述:** plan 中多次引用 `ai-tools-bridge/skills/sdd-review-spec/spec-reviewer-prompt.md`，路径是正确的（已验证文件存在）。tasks.md 4.1 中引用的路径是 `skills/sdd-review-spec/spec-reviewer-prompt.md`（相对路径）。两者指向同一文件，无问题，仅作记录。

plan.md 质量良好，tasks.md 全部 22 个子任务均有覆盖，文件路径均已验证存在，验证命令基本可执行。主要建议修复执行顺序图的矛盾标注。其余 minor/info 级问题不阻碍执行，但建议在后续 plan 编写中注意保持 TDD 结构一致性。
