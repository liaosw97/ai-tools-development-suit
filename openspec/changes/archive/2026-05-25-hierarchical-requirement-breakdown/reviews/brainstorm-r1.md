# Brainstorm Review — Round 1

**审查对象:** brainstorm.md
**日期:** 2026-05-24

## 总结

brainstorm.md 整体质量较高，方案探索充分，决策清晰且有明确的理由和被否决的替代方案。功能拆分设计详细，覆盖了三个核心阶段（brainstorm、plan、code）的具体改动。但存在几个需要关注的问题：缺少边界条件和异常流的考虑、部分决策缺乏可验证的成功标准、以及"未解决的问题"部分声明过于绝对。

## Issues

### [severity: major] 缺少边界条件和异常流考虑

- **位置:** brainstorm.md §方案探索、§关键决策
- **描述:** brainstorm 聚焦于正常流程（L1→L2→L3 拆分、按序实现），但未考虑以下边界场景：
  1. 用户中途取消拆分流程如何处理？
  2. 拆分过程中发现需求本身有矛盾或无法拆分怎么办？
  3. 功能单元间存在循环依赖如何处理？
  4. 目录冲突检测发现多个相似目录时，用户选择"新建目录"但路径冲突如何处理？
- **建议:** 在"关键决策"或"功能拆分设计"中补充异常流处理策略，或明确标注这些场景将在 spec/plan 阶段细化。

### [severity: major] "未解决的问题"声明过于绝对

- **位置:** brainstorm.md §未解决的问题
- **描述:** 声明"无。所有关键问题已在探索过程中解决。"过于绝对。实际上存在以下待细化问题：
  1. 功能树解析的具体算法未定义（如何从 Markdown 中可靠提取层级结构）
  2. 依赖检测的"潜在依赖"判断标准未明确（什么程度的关联算"潜在依赖"？）
  3. "相似目录"的相似度阈值未定义
- **建议:** 将"未解决的问题"改为"待细化问题"，列出需要在后续阶段（spec/plan）或实现时解决的技术细节。

### [severity: minor] 部分决策缺乏可验证的成功标准

- **位置:** brainstorm.md §决策 3、§决策 5
- **描述:**
  - 决策 3（依赖处理方式）选择"默认独立 + 异常提示"，但未定义"异常提示"的触发条件是什么，如何验证 AI 正确检测了依赖风险。
  - 决策 5（拆分层数控制）选择"用户可干预"，但未定义 AI 建议继续拆分的判断标准。
- **建议:** 补充可量化的判断标准，例如"当功能单元包含超过 3 个独立操作时建议继续拆分"，或明确标注将在 spec 阶段定义具体规则。

### [severity: minor] 配置扩展未说明默认值选择理由

- **位置:** brainstorm.md §配置扩展
- **描述:** `default-depth: 3` 的默认值选择未说明理由。为什么是 3 层而不是 2 层或 4 层？
- **建议:** 补充选择 3 层作为默认值的理由，例如"基于常见业务系统的功能粒度经验值"。

### [severity: minor] 目录冲突检测的"相似"定义模糊

- **位置:** brainstorm.md §sdd-brainstorm 改动、§sdd-code 改动
- **描述:** 两处提到"相似目录"或"相似功能目录"，但未定义"相似"的判断标准（名称相似？功能相似？路径相似？）。
- **建议:** 补充相似度判断的具体规则，例如"目录名称包含相同关键词且路径深度相同"。
