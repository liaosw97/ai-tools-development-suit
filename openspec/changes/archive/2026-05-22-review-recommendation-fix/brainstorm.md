# Brainstorm — 审查推荐下一步问题修复

## 问题陈述

用户反馈 SDD 工作流中多个审查类 skill（`sdd-review-code`、`sdd-review-spec`、`sdd-verify`）的"推荐下一步"存在以下问题：

1. **无修复选项**：审查发现问题时，仅提示"有问题需修复"，但不给出具体修复选项（如 `/sdd-code` 或 `/sdd-test-code`）
2. **选项重复**：推荐列表中出现重复的选项
3. **描述不准确**：推荐选项的描述与实际不符
4. **格式不统一**：
   - 有的使用"推荐下一步:"后紧跟"★ 推荐下一步:"
   - 有的标识错位，"★ 推荐下一步:"出现在"推荐下一步:"之前
   - 各 skill 的推荐格式不一致

## 方案探索

### 方案 A：统一推荐格式模板

**核心思路**：定义一个标准化的"推荐下一步"格式模板，所有 skill 后置逻辑必须遵循。

**格式模板**：
```
推荐下一步:
  - [条件描述] → ★ [推荐命令] — [简短说明]
  - [其他条件] → ○ [可选命令] — [简短说明]

★ 推荐下一步: [主推荐命令] — [简短说明]
  ○ [备选命令] — [备选说明]
  ○ [其他备选] — [其他说明]
```

**优点**：
- 格式统一，易于阅读
- 明确区分主推荐和备选
- 简洁的选项列表 + 展开的推荐详情

**缺点**：
- 需要修改所有 skill 的 SKILL.md
- 需要确保模板在各场景下适用

### 方案 B：简化为单行推荐

**核心思路**：简化为只输出一个明确的"★ 推荐下一步"行，备选项用列表形式呈现。

**格式模板**：
```
★ 推荐下一步: [主推荐命令] — [简短说明]
  ○ /sdd-xxx — [备选说明]
  ○ /sdd-yyy — [其他备选说明]
```

**优点**：
- 极简，无重复
- 突出主推荐

**缺点**：
- 失去"推荐下一步:"列表的概览性
- 条件性推荐（根据审查结果）无法清晰呈现

### 方案 C：条件驱动的推荐

**核心思路**：根据审查结果动态生成推荐，使用条件判断明确区分场景。

**格式模板**：
```
★ 推荐下一步（按审查结果）:
  [APPROVED/PASSED] → /sdd-[下一步] — [说明]
  [NEEDS_REVISION/FAILED] → /sdd-[修复命令] — [说明]
  ○ /sdd-[备选] — [备选说明]
```

**优点**：
- 明确关联审查结果与推荐动作
- 解决"无修复选项"问题

**缺点**：
- 格式与其他 skill 需协调统一

## 问题定位

### 1. sdd-review-code (SKILL.md:172-177)

**当前代码**：
```
推荐下一步:
  - 有 PARTIAL/MISSING 场景 → ★ /sdd-test-code 补全缺失测试
  - 全部 PASSED → ★ /sdd-verify 全面验证
  - 有 critical issues → 修复后重新 /sdd-review-code
  - 有更多批次 → /sdd-code 继续实施
```

**问题分析**：
1. ❌ 格式混乱：列表项内嵌套"★"符号，与标准格式不一致
2. ❌ 第 3 行"修复后重新 /sdd-review-code"缺少 ★ 和说明，且无具体修复路径
3. ❌ 第 4 行"/sdd-code 继续实施"缺少 ★ 和说明
4. ❌ 未区分 Phase 1 问题（spec 合规）和 Phase 2 问题（代码质量）的修复路径

### 2. sdd-review-spec (SKILL.md:116-120)

**当前代码**：
```
★ 推荐下一步（按审查结果）:
  Approved → /sdd-plan — 生成实施计划
  Issues → /sdd-propose — 修正提案后重新生成
  ○ /sdd-ff — 快进生成剩余文档
```

**问题分析**：
1. ✅ 格式相对正确：使用条件驱动
2. ❌ "Issues → /sdd-propose"描述不准确：spec 审查问题应通过修改 spec 或 proposal 修复，而非"修正提案后重新生成"
3. ❌ 缺少直接修复 spec 的选项：如 `/sdd-ff`（重新生成 spec）

### 3. sdd-verify (SKILL.md:122-142)

**当前代码**：
```
推荐下一步:
  - Pass → /sdd-ship 归档合并
  - Fail → /sdd-code 补充缺失实现

未覆盖场景:
  - spec:auth#token-refresh — 需要补充测试

推荐下一步:
  - 通过 → /sdd-ship 归档合并
  - 未通过 → /sdd-code 补充缺失的实现

★ 推荐下一步: /sdd-ship — 归档合并
  ○ /sdd-code — 修复验证失败项
```

**问题分析**：
1. ❌ **严重重复**：出现 3 次"推荐下一步"，其中第 1 次和第 2 次内容几乎相同
2. ❌ 格式错位：第 1 次"推荐下一步"在验证报告中间，应只在完成引导中输出
3. ❌ 第 3 次"★ 推荐下一步:"格式正确，但前两次输出导致混乱

### 4. sdd-test-code (SKILL.md:113-116)

**当前代码**：
```
推荐下一步:
  ★ /sdd-verify — 全面验证 Spec 场景覆盖
  ○ /sdd-ship — 归档合并（sdd-ship 会提示 verify 检查）
```

**问题分析**：
1. ✅ 格式相对正确
2. ❌ 使用"★"在列表项内，与标准格式不一致

## 关键决策

### 决策 1：统一推荐格式标准

**选择 [方案 A 的简化版] 而非 [方案 B 或 C]**：

**原因**：
- 方案 A 保持概览性列表 + 展开详情的双层结构，信息层级清晰
- 方案 B 过于简化，无法处理条件性推荐
- 方案 C 的条件驱动格式适用于审查类 skill，但需融入统一模板

**统一格式标准**：

**普通 skill 格式**：
```
★ 推荐下一步: /sdd-[主推荐] — [说明]
  ○ /sdd-[可选] — [可选说明]
  △ /sdd-[备选] — [备选说明]
```

**审查类 skill 条件驱动格式**：
```
★ 推荐下一步（按审查结果）:
  /sdd-[PASSED路径] — [通过时的说明]
  /sdd-[FAILED路径] — [失败时的修复说明]
  △ /sdd-[备选] — [备选说明]
```

> 优先级说明：★ 主推荐 | ○ 可选项 | △ 备选项（可跳过）
> 审查类格式说明：多行指令按审查结果选择执行，非并列关系。

**规则**：
1. 第一层"推荐下一步:"提供条件概览（最多 4 行）
2. 第二层"★ 推荐下一步:"提供具体展开
3. 每个条件项内使用 ★/○ 标识优先级
4. 审查类 skill 使用"按审查结果"作为条件

### 决策 2：审查问题必须提供修复路径

**选择 [明确修复路径] 而非 [笼统提示"修复后重新"]**：

**原因**：
- 用户反馈明确指出"有问题提示进行修复，但是没有给出选项建议"
- 审查发现的问题类型不同，修复路径不同：
  - Spec 合规问题 → `/sdd-code` 补充实现
  - 代码质量问题 → `/sdd-code` 修复代码 或 `/sdd-test-code` 修复测试
  - Spec 质量问题 → `/sdd-ff` 重新生成 或手动编辑

**修复路径表**：

| 审查类型 | 问题类型 | 修复路径 |
|---------|---------|---------|
| sdd-review-code Phase 1 | PARTIAL/MISSING 场景（测试缺失） | `/sdd-test-code` 补全测试 |
| sdd-review-code Phase 1 | MISSING 场景（实现缺失） | `/sdd-code` 补充实现 |
| sdd-review-code Phase 1.5 | 规范扫描问题 | `/sdd-code` 修复代码 |
| sdd-review-code Phase 2 | critical/major issues | `/sdd-code` 修复代码 |
| sdd-review-spec | spec 质量问题 | `/sdd-ff` 重新生成 或手动修复 spec |
| sdd-verify | 测试未覆盖场景 | `/sdd-test-code` 补充测试 |
| sdd-verify | 实现缺失 | `/sdd-code` 补充实现 |

> **区分逻辑**：PARTIAL 场景（部分实现）→ 补全测试；MISSING 场景（完全未实现）→ 补充实现。

### 决策 3：消除重复输出

**选择 [单一输出点] 而非 [多处输出]**：

**原因**：
- sdd-verify 的验证报告中不应出现"推荐下一步"
- "推荐下一步"只在"完成引导"节输出一次
- 中间过程的输出（如未覆盖场景列表）不应包含推荐
