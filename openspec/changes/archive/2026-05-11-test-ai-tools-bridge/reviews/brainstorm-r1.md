# Brainstorm Review — Round 1

**审查对象:** brainstorm.md
**日期:** 2026-05-10

## 总结

brainstorm 整体结构清晰，方案比较充分，5 个关键决策均有明确结论、理由和被否决的替代方案。约束识别涵盖了主要技术和团队约束。主要不足在于：(1) 需求描述中对 11 个 skill 的覆盖范围没有逐一说明，遗漏了子代理审查提示词（reviewer-prompt）的测试场景；(2) 方案比较表中 B 列的"可重复"评为"中"缺少论证；(3) 存在一个明显的 YAGNI 偏差——L3 集成场景被纳入方案但无法自动化，其作为测试体系的价值存疑；(4) 未识别性能和兼容性方面的技术约束。

## Issues

### [severity: major] 需求覆盖不完整——缺少子代理审查提示词和 guideline 的测试
- **位置:** brainstorm.md §需求描述
- **描述:** 需求描述列出了"11 个 skill 定义、7 个制品模板、1 个 schema 定义和 4 个策略文档"，但方案探索和决策中只关注了 SKILL.md 的 YAML frontmatter 和模板占位符。未覆盖以下文件的测试：(1) `skills/sdd-*/*-reviewer-prompt.md`（5 个子代理审查提示词，如 `brainstorm-reviewer-prompt.md`、`plan-reviewer-prompt.md` 等）；(2) `guidelines/` 下的 4 个策略文档的内容合规性。这些文件是插件的重要组成部分，应明确是否纳入测试范围以及理由。
- **建议:** 在需求描述中补充完整的文件清单，对 reviewer-prompt 和 guideline 文件明确说明是纳入测试还是排除（并给出排除理由）。如果纳入，L1 结构验证应增加对这些文件的校验规则。

### [severity: major] L3 集成场景的定位模糊——YAGNI 嫌疑
- **位置:** brainstorm.md §方案探索 §决策 2 §决策 4
- **描述:** L3 集成场景被定义为"人工参考"，使用 GIVEN/WHEN/THEN 格式写成 Markdown 文件。然而：(1) 它不能自动化执行，不产生 pass/fail 结果；(2) 它不是真正的测试，而是行为文档；(3) 决策 4 选择用 OpenSpec spec 格式的理由是"dogfooding"，但这更像是设计偏好而非测试需求。对于一个当前零测试覆盖的项目，在第一轮就投入 11 个场景文件（约占全部交付物的 40%）写人工参考文档，有过度设计倾向。
- **建议:** 将 L3 从本次测试体系建设中拆分出来，作为后续独立需求处理。当前聚焦 L1 和 L2 的自动化测试，确保核心覆盖先落地。如果保留 L3，应明确其验收标准——什么条件下 L3 算"完成"。

### [severity: minor] 方案比较表中部分评分缺少论证
- **位置:** brainstorm.md §方案比较
- **描述:** 方案 B（单一脚本）的"可重复"评为"中"，但脚本天然是可重复执行的，这个评分与方案描述矛盾。方案 C 的"覆盖深度"评为"行为层"，但方案 C 的描述中说的是"人工验证"，并没有明确说明能覆盖什么层次。这些不一致会影响决策可信度。
- **建议:** 为方案 B 的"可重复"提供评分为"中"的理由（例如"脚本输出无结构化断言，不同运行间结果不可比较"），或修正为"高"。对方案 C 的覆盖深度补充说明。

### [severity: minor] 技术约束遗漏——yaml 库版本兼容性和性能约束
- **位置:** brainstorm.md §约束识别 §技术约束
- **描述:** 决策 3 选择了 `yaml` npm 包但未指定版本范围。技术约束中未提及：(1) yaml 解析的性能约束——如果 SKILL.md 文件增大，解析开销是否可接受；(2) vitest 版本与现有 `openspec/vitest.config.ts` 的兼容性要求；(3) Node.js 最低版本要求。这些约束对实现有直接影响。
- **建议:** 在技术约束中补充依赖版本兼容性要求。明确 `yaml` 和 `vitest` 的版本约束，以及 Node.js 最低版本。

### [severity: minor] 未考虑 CI 集成的具体约束
- **位置:** brainstorm.md §约束识别 §团队约束
- **描述:** 决策 5 提到"便于 CI 配置"作为测试目录结构的理由，但约束识别中没有说明 CI 环境的具体要求（如运行平台、Node.js 版本、是否需要 coverage 报告、CI 触发条件等）。这会导致后续实现时缺乏明确的 CI 集成标准。
- **建议:** 在团队约束中补充 CI 相关要求，或在决策中明确"本次不涉及 CI 配置，仅确保本地可运行"。

### [severity: minor] "16 个自动化测试 + 11 个场景文件"的工作量估算缺乏依据
- **位置:** brainstorm.md §方案探索 §方案 A
- **描述:** 方案 A 的缺点中提到"约 16 个自动化测试 + 11 个场景文件"，但 brainstorm 中没有任何拆解说明这 16 个测试分别是什么、11 个场景文件对应哪些 skill。这个数字如果只是估算，应标注为估算；如果是具体规划，应列出清单。
- **建议:** 要么删除这个具体数字改为定性描述（"测试代码量较多"），要么补充测试清单的概要拆解。
