# Brainstorm: test-ai-tools-bridge

> 深度探索记录 — 为 ai-tools-bridge 插件建立分层测试体系，验证其结构合规性和流程编排正确性

## 需求描述

ai-tools-bridge 是一个纯 Markdown 的 Claude Code 插件（v0.2.0），实现了 SDD（规格驱动开发）工作流编排器。当前没有任何测试覆盖。

### 待测文件清单

| 类别 | 文件 | 数量 | 纳入 L1 | 纳入 L2 |
|------|------|------|---------|---------|
| Skill 定义 | `skills/sdd-*/SKILL.md` | 11 | frontmatter + 结构 | 委托关系 + 覆盖指令 |
| 审查提示词 | `skills/sdd-*/*-reviewer-prompt.md` | 5 | 存在性 + 格式 | 审查维度完整性 |
| 制品模板 | `schemas/sdd/templates/*.md` | 7 | 占位符 vs schema | — |
| Schema | `schemas/sdd/schema.yaml` | 1 | 合法 YAML | 依赖链一致性 |
| 策略文档 | `guidelines/*.md` | 4 | 存在性 | — |
| 插件元数据 | `.claude-plugin/plugin.json` | 1 | 合法 JSON + 必填字段 | — |

用户需要一套**分层测试体系**来验证：
1. **文件结构合规（L1）**：上述所有文件的格式正确性、字段完整性、占位符与 schema 一致性
2. **流程编排正确（L2）**：依赖链完整性、审查循环配置、覆盖指令一致性、制品状态转换可达性

## 方案探索

### 方案 A: 分层测试套件

用 Node.js + vitest 构建三层自动化测试：L1 结构验证、L2 编排验证、L3 集成场景（Markdown）。

- **优点:**
  - 分层清晰，每层可独立运行
  - L1/L2 完全自动化，可纳入 CI
  - vitest 与 OpenSpec 项目技术栈一致
  - 测试可重复执行，支持回归验证
- **缺点:**
  - 需要引入 yaml 解析依赖
  - L1 预估 9-12 个测试用例，L2 预估 6-8 个测试用例，总量约 15-20 个

### 方案 B: 单一验证脚本

一个 `validate.mjs` 脚本顺序检查所有约束，输出 pass/fail 报告。

- **优点:**
  - 零依赖（只用 Node.js 内置 fs 模块）
  - 实现快速
- **缺点:**
  - 无测试框架的断言、报告能力
  - 不易扩展和维护
  - 无法覆盖集成测试层

### 方案 C: OpenSpec 自举

用 SDD 自身流程创建 test-sdd 变更，spec 描述预期行为，人工验证。

- **优点:**
  - dogfooding，验证工具本身
- **缺点:**
  - 无法自动化，不适合回归
  - 依赖人工执行，不可重复

### 方案比较

| 维度 | A 分层套件 | B 单一脚本 | C 自举 |
|------|-----------|-----------|--------|
| 自动化 | L1/L2 全自动 | 全手动流程 | 全人工 |
| 可重复 | 高 | 高（脚本可重复但输出无结构化断言） | 低 |
| 维护性 | 高 | 低 | 中 |
| 覆盖深度 | L1 结构 + L2 编排 | 仅结构层 | 仅行为层（人工） |
| 实现成本 | 中 | 低 | 中 |

**选择方案 A**：分层测试套件。它在自动化、可重复性和覆盖深度上均优于其他方案，且与项目技术栈一致。

## 关键决策

### 决策 1: 测试框架选择 vitest
- **选择:** 使用 vitest 作为测试框架
- **理由:** OpenSpec 项目已使用 vitest（`openspec/vitest.config.ts`），保持技术栈一致性；vitest 原生支持 TypeScript，测试代码类型安全
- **被否决的替代:** Jest（功能更强但引入更多依赖，与项目现有栈不一致）

### 决策 2: 本次聚焦 L1/L2 自动化测试
- **选择:** 本次只实现 L1 结构验证 + L2 编排验证，不做 L3 集成场景
- **理由:** 项目当前零测试覆盖，应优先落地可自动化、可回归的核心测试。L3 集成场景需人工执行，无法自动化验证，作为行为文档其价值需独立评估
- **被否决的替代:** 同时做 L3（第一轮投入产出比不合理，人工场景文件约占 40% 交付量但不产生自动化价值）

### 决策 3: YAML 解析用 yaml 库
- **选择:** 使用 `yaml` npm 包解析 YAML frontmatter 和 schema.yaml
- **理由:** SKILL.md 使用 YAML frontmatter（`---` 分隔），需要可靠的 YAML 解析器；Node.js 内置无 YAML 支持
- **被否决的替代:** 正则提取（脆弱，难以处理多行值和嵌套结构）

### 决策 4: reviewer-prompt 纳入 L1/L2 测试
- **选择:** 5 个 `*-reviewer-prompt.md` 文件纳入测试：L1 验证存在性和格式，L2 验证审查维度覆盖完整性
- **理由:** 审查提示词是 SDD 质量保证的核心组件，其正确性直接影响 review 循环的有效性
- **被否决的替代:** 仅测试存在性（不够，空的或格式错误的 reviewer-prompt 会导致审查维度缺失）

### 决策 5: 测试放置于 tests/ 目录
- **选择:** 测试代码放在 `ai-tools-bridge/tests/` 下，与源文件分离
- **理由:** 标准项目布局，不污染 skill 定义目录；便于 CI 配置
- **被否决的替代:** 与 skill 文件同目录（会干扰 Claude Code 的 skill 发现机制）

## 约束识别

### 技术约束
- 插件是纯 Markdown，无运行时代码——测试只能是静态分析
- SKILL.md 的 YAML frontmatter 格式需精确解析（`---` 分隔的头部）
- 模板使用 HTML 注释占位符（`<!-- ... -->`），需正则匹配验证
- 交叉引用验证需要知道可用技能的完整列表（superpowers + openspec 的 skill 名称）
- 依赖版本兼容性：vitest 需与 `openspec/vitest.config.ts` 中版本一致；`yaml` 库需兼容 Node.js 18+
- 本次不涉及 CI 配置，仅确保本地 `npx vitest run` 可运行

### 团队约束
- 测试应与现有 OpenSpec 技术栈一致（vitest + TypeScript）
- 测试文件使用中文注释，与项目 CLAUDE.md 语言规则一致
- 测试应可独立运行，不依赖 Claude Code 运行时
