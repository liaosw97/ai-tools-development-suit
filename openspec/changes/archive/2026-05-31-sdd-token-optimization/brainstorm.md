# Brainstorm: SDD Token 优化

> 深度探索记录 — 记录需求探索过程和关键决策

## 需求描述

分析 ai-tools-bridge 使用 OpenSpec 和 Superpowers 的完整工作流，检测各个阶段的 token 消耗，在不影响精度（输出质量和工作流完整性）的前提下进行优化。

**核心目标**：
- 建立完整的 token 预算视图（定义层 + 执行层）
- 同时优化峰值消耗（context window 占用）和总消耗（成本）
- 保持精度：brainstorm 方案完整性、spec 场景覆盖度、review 循环充分性、TDD 步骤严格性

## 方案探索

### 方案 A: 懒加载 + 模块化拆分

**核心思路**：将大型 skill 拆分为独立模块，按需加载。

**具体措施**：
1. 拆分 sdd-brainstorm（472行 → 3个模块）
   - 核心流程（~150行）
   - 角色系统（~100行，按需加载）
   - 拆分模式（~100行，按需加载）
2. Guidelines 按需加载
   - token-optimization.md：仅在初始化时加载
   - quality-checkpoints.md：仅在质量门检查时加载对应部分
   - decision-strategy.md：仅在决策点加载
3. Review Prompt 延迟加载
   - 仅在进入 review 循环时加载对应的 reviewer prompt

- **优点:**
  - 峰值消耗降低 30-40%
  - 不影响精度（所有逻辑保留，只是延迟加载）
  - 实施复杂度中等

- **缺点:**
  - 总消耗仅降低 10-15%（延迟加载 ≠ 不加载）
  - 需要重构 skill 文件结构

### 方案 B: 上下文压缩 + 摘要传递

**核心思路**：压缩传递给 subagent 的上下文，使用摘要代替完整内容。

**具体措施**：
1. Artifact 摘要传递
   - 传递 spec 场景列表（而非完整 spec 文件）
   - 传递 task 摘要（而非完整 tasks.md）
2. Review 上下文压缩
   - 只传递 diff + 相关 spec 场景（而非完整文件）
   - 使用结构化摘要代替自然语言描述
3. 跨 Action 状态压缩
   - 维护轻量级状态文件（~200 tokens）
   - 记录关键决策和进度，而非完整历史

- **优点:**
  - 总消耗降低 35-45%
  - 峰值消耗降低 10-15%
  - 与现有 token-optimization.md 策略一致

- **缺点:**
  - 精度风险：摘要可能丢失细节
  - 需要验证覆盖率是否下降
  - 实施复杂度高

### 方案 C: 混合方案（A + B 的平衡版）

**核心思路**：结合懒加载和选择性压缩，在关键环节保留完整上下文。

**具体措施**：
1. 懒加载 Skill 定义（方案 A 的核心）
2. 选择性压缩（方案 B 的安全部分）
3. 保留关键环节的完整上下文（brainstorm、code、review 阶段）

- **优点:**
  - 峰值消耗降低 25-35%
  - 总消耗降低 20-30%
  - 精度影响低

- **缺点:**
  - 不是最优解
  - 实施复杂度中高

### 方案 D: A + B 组合（最终选择）

**核心思路**：同时实施懒加载和上下文压缩，最大化优化效果。

**具体措施**：
1. **懒加载**（方案 A 全部内容）
   - 拆分大型 skill
   - 按需加载 guidelines
   - 延迟加载 reviewer prompt

2. **上下文压缩**（方案 B 全部内容）
   - Artifact 摘要传递
   - Review 上下文压缩
   - 跨 Action 状态压缩

3. **精度验证机制**
   - 小范围测试验证精度
   - 对比优化前后的输出质量
   - 建立精度监控指标

- **优点:**
  - 峰值消耗降低 30-40%
  - 总消耗降低 40-50%
  - 最大化优化效果

- **缺点:**
  - 实施复杂度高
  - 需要精度验证成本
  - 改动范围大

### 方案比较

| 方案 | 峰值优化 | 总消耗优化 | 精度影响 | 实施复杂度 |
|------|----------|------------|----------|------------|
| A | 30-40% | 10-15% | 无 | 中 |
| B | 10-15% | 35-45% | 需验证 | 高 |
| C | 25-35% | 25-35% | 低 | 中高 |
| **D** | **30-40%** | **40-50%** | **需验证** | **高** |

**选择方案 D 的理由**：
1. 用户关心峰值和总消耗，需要最大化优化
2. 用户接受精度验证成本
3. 现有 token-optimization.md 已在做类似压缩，有基础
4. 可分阶段实施，先做懒加载，再做压缩

## 关键决策

### 决策 1: 优化方案选择
- **选择:** 方案 D（A + B 组合）
- **理由:** 同时优化峰值和总消耗，最大化效果，用户接受精度验证成本
- **被否决的替代:** 
  - 方案 A：总消耗优化有限（仅 10-15%）
  - 方案 C：折中方案，不是最优解

### 决策 2: 精度验证策略
- **选择:** 小范围测试 + 对比验证
- **理由:** 风险可控，可分阶段验证
- **被否决的替代:** 
  - 不验证直接上线：风险太高
  - 全量测试再上线：成本太高

### 决策 3: 实施顺序
- **选择:** 先懒加载，后上下文压缩
- **理由:** 懒加载风险低，可快速见效；压缩需要更多验证
- **被否决的替代:** 
  - 同时实施：风险集中
  - 先压缩后懒加载：压缩风险高，先做不安全

## 成功标准

### 量化验收标准

| 指标 | 目标值 | 回滚阈值 | 测量方法 |
|------|--------|----------|----------|
| 峰值 token 消耗 | 降低 ≥30% | 降低 <15% | 单个 action 执行时测量 context 占用 |
| 总 token 消耗 | 降低 ≥35% | 降低 <20% | 完整流程累计消耗 |
| brainstorm 方案完整性 | ≥2 个候选方案 | <2 个方案 | 检查 brainstorm.md |
| spec 场景覆盖度 | 100% 场景有 GIVEN/WHEN/THEN | <90% 覆盖 | 统计 spec 文件中的场景数 |
| review 循环充分性 | 最多 3 轮，通过率 ≥80% | 通过率 <60% | 统计 review 结果 |
| TDD 步骤严格性 | 每个任务有 RED/GREEN | 缺失率 >10% | 检查 plan.md |

### 回滚策略

**分阶段回滚**：
1. **懒加载回滚**：恢复原始 skill 文件结构，删除拆分后的模块文件
2. **上下文压缩回滚**：恢复完整 artifact 传递，删除摘要生成逻辑
3. **全量回滚**：git revert 到优化前的 commit

**回滚触发条件**：
- 任一指标低于回滚阈值
- 精度验证发现关键问题
- 用户反馈质量下降

**回滚操作**：
```bash
# 分阶段回滚
git revert <懒加载 commit>
git revert <压缩 commit>

# 全量回滚
git revert <优化起始 commit>..<优化结束 commit>
```

## 精度验证方案

### 测试范围

**选择 3 个典型变更进行验证**：
1. **简单变更**（1-2 个 spec 场景，≤5 个 tasks）
2. **中等变更**（4-6 个 spec 场景，6-15 个 tasks）
3. **复杂变更**（>8 个 spec 场景，>15 个 tasks）

**每个变更执行完整流程**：
- brainstorm → propose → ff → plan → code → review → verify → ship

### 对比方法

**优化前基线**：
- 使用当前版本执行相同变更
- 记录每个 action 的 token 消耗
- 记录输出质量指标

**优化后对比**：
- 使用优化版本执行相同变更
- 记录相同指标
- 计算差异

**对比维度**：
1. Token 消耗（峰值 + 总量）
2. brainstorm 方案数量和质量评分
3. spec 场景覆盖度
4. review 发现的问题数量
5. 代码质量和测试覆盖率

### 通过标准

**精度验证通过**：
- 所有量化指标达到目标值
- 无 critical 问题
- 人工审核确认输出质量未下降

**精度验证失败**：
- 任一指标低于回滚阈值
- 发现关键信息丢失
- 人工审核发现质量问题

## 异常流处理

### 懒加载失败

**场景**：模块文件不存在或加载超时

**处理**：
1. 降级到完整加载（使用原始 skill 文件）
2. 记录错误日志
3. 继续执行，不阻断流程

**预防**：
- 模块文件完整性检查
- 加载超时设置（默认 5 秒）
- 备份原始 skill 文件

### 摘要丢失信息

**场景**：摘要算法丢失关键信息

**处理**：
1. 检测：对比摘要和原文的关键字段
2. 降级：使用完整 artifact 传递
3. 记录：标记摘要质量问题

**预防**：
- 关键字段强制保留（spec 场景、task 链接、决策结论）
- 摘要质量检查（关键信息覆盖率 ≥95%）
- 人工抽检摘要质量

### 状态文件损坏

**场景**：状态文件格式错误或内容损坏

**处理**：
1. 检测：验证文件格式和内容完整性
2. 降级：忽略状态文件，从 artifact 重新构建
3. 重建：生成新的状态文件

**预防**：
- 文件格式校验（JSON Schema）
- 定期备份状态文件
- 写入时原子操作

## 约束识别

### 技术约束
- Skill 文件需要重构，保持向后兼容
- 摘要生成需要算法支持，不能丢失关键信息
- 状态文件需要设计格式，支持跨 action 传递
- 需要处理懒加载和摘要的异常情况

### 团队约束
- 需要精度验证，需要人工审核（2-3 人天）
- 改动范围大，需要充分测试（回归测试 + 精度测试）
- 需要更新文档和指南（token-optimization.md 等）
- 总成本 9-12 人天，需要项目排期
