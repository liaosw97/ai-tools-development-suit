# Brainstorm Review — Round 1

**审查对象:** brainstorm.md
**日期:** 2026-05-30

## 总结

brainstorm.md 对 SDD Token 优化需求进行了系统性的方案探索，提出了 4 个方案并做出了明确的选择（方案 D）。文档结构清晰，决策有理有据。但在精度验证的具体方法、成功/失败标准的量化定义、以及异常情况的回滚策略方面存在明显不足，需要补充完善后才能为后续 proposal 提供充分的决策基础。

## Issues

### [severity: critical] 缺少明确的成功标准和量化指标
- **位置:** brainstorm.md §需求描述、§方案比较
- **描述:** 文档提到"峰值消耗降低 30-40%"、"总消耗降低 40-50%"等预期效果，但这些是估算值而非成功标准。缺少明确的验收标准，例如：优化后必须达到什么阈值才算成功？低于什么阈值需要回滚？
- **建议:** 在"关键决策"部分新增"决策 4: 成功标准"，定义：
  - 峰值优化目标（如：≥25%）
  - 总消耗优化目标（如：≥30%）
  - 精度保持标准（如：场景覆盖率 ≥95%）
  - 回滚触发条件（如：精度下降 >5%）

### [severity: critical] 缺少回滚策略
- **位置:** brainstorm.md §关键决策、§未解决的问题
- **描述:** 方案 D 的精度影响标注为"需验证"，但未说明如果验证失败如何回滚。改动范围大（涉及 skill 文件重构、摘要算法、状态文件），一旦出现问题，如何快速恢复到优化前状态？
- **建议:** 补充回滚策略：
  - 是否支持特性开关（feature flag）？
  - 是否可以分阶段发布，每阶段独立验证？
  - 回滚操作的具体步骤是什么？

### [severity: major] 精度验证方法不够具体
- **位置:** brainstorm.md §关键决策 → 决策 2
- **描述:** 决策 2 选择"小范围测试 + 对比验证"，但未定义：
  - "小范围"的具体范围是什么（哪些 action？多少个测试用例？）
  - "对比验证"的具体方法是什么（人工审核？自动对比？指标是什么？）
  - 验证的通过/失败标准是什么
- **建议:** 细化精度验证策略：
  - 定义测试范围（如：选择 3 个典型需求，覆盖 brainstorm/plan/code 阶段）
  - 定义对比方法（如：对比优化前后的 spec 场景覆盖率、review 发现的问题数）
  - 定义通过标准（如：覆盖率差异 ≤3%，无 critical 问题遗漏）

### [severity: major] 边界条件和异常流处理缺失
- **位置:** brainstorm.md §方案 D → 具体措施
- **描述:** 方案涉及多个技术改动，但未考虑异常情况：
  - 懒加载失败时如何处理？（网络问题、文件损坏）
  - 摘要丢失关键信息如何检测和补救？
  - 状态文件损坏或丢失如何恢复？
  - 不同模型对压缩内容的理解能力差异？
- **建议:** 在"技术约束"部分补充异常处理策略，或在"未解决的问题"中明确列出。

### [severity: minor] 精度监控指标可能属于 YAGNI
- **位置:** brainstorm.md §方案 D → 精度验证机制
- **描述:** "建立精度监控指标"可能超出了当前需求范围。如果优化是一次性任务而非持续过程，建立完整的监控体系可能是过度设计。
- **建议:** 明确优化是否为持续性工作。如果是一次性优化，可以用人工验证代替自动化监控。

### [severity: minor] 实施成本估算不足
- **位置:** brainstorm.md §方案比较
- **描述:** 文档标注了实施复杂度（中/高），但未估算具体的工作量（人天）。这会影响实施计划的制定。
- **建议:** 在方案比较表中增加"预估工作量"列，为后续 plan 阶段提供参考。

- [x] 决策清晰度 — 3 个关键决策都有明确结论和理由
