## Context

当前 ai-tools-bridge SDD 工作流存在 token 消耗过高的问题：

**定义层**：
- SDD Skills (14个)：2,716 行，~13,500 tokens
- Superpowers Skills：3,207 行，~16,000 tokens
- Templates (8个)：274 行，~1,400 tokens
- Reviewer Prompts (7个)：556 行，~2,800 tokens
- 总计：~36,800 tokens（完整加载时）

**执行层**：
- 单个 Action：5,600-12,000 tokens（平均 ~8,000）
- 完整流程（中等复杂度）：~113,000 tokens

**问题**：
- 峰值消耗高：单个 action 可能超出 context window
- 总消耗高：完整流程成本高
- 无系统化的优化策略

## Goals / Non-Goals

**Goals:**
- 峰值 token 消耗降低 ≥30%
- 总 token 消耗降低 ≥35%
- 保持精度（输出质量和工作流完整性）
- 建立 token 预算视图（定义层 + 执行层）

**Non-Goals:**
- 不修改 Superpowers 核心 skill
- 不改变工作流顺序和依赖关系
- 不减少 review 循环次数
- 不简化质量门检查点

## Decisions

### 决策 1: 懒加载实现方式

**选择**：模块化拆分 + 动态加载

**理由**：
- 将大型 skill 拆分为独立模块（核心流程、角色系统、拆分模式）
- 按需加载 guidelines 和 reviewer prompt
- 峰值消耗降低 30-40%

**替代方案**：
- 完整加载 + 缓存：峰值消耗不降低
- 配置化加载：复杂度高，维护成本大

### 决策 2: 上下文压缩策略

**选择**：摘要传递 + 结构化压缩

**理由**：
- Artifact 摘要传递：传递 spec 场景列表、task 摘要（而非完整文件）
- Review 上下文压缩：传递 diff + 相关 spec 场景（而非完整文件）
- 跨 Action 状态压缩：维护轻量级状态文件（~200 tokens）
- 总消耗降低 40-50%

**替代方案**：
- 完整传递：总消耗不降低
- 仅传递 diff：可能丢失上下文

### 决策 3: 精度验证方法

**选择**：小范围测试 + 对比验证

**理由**：
- 选择 3 个典型变更（简单、中等、复杂）
- 对比优化前后的输出质量
- 风险可控，可分阶段验证

**替代方案**：
- 不验证直接上线：风险太高
- 全量测试再上线：成本太高

### 决策 4: 实施顺序

**选择**：先懒加载，后上下文压缩

**理由**：
- 懒加载风险低，可快速见效
- 压缩需要更多验证，先做不安全
- 可分阶段实施，降低风险

**替代方案**：
- 同时实施：风险集中
- 先压缩后懒加载：压缩风险高，先做不安全

## Risks / Trade-offs

### 精度风险
- **风险**：摘要可能丢失关键信息
- **缓解**：关键字段强制保留（spec 场景、task 链接、决策结论）+ 人工抽检
- **监控**：摘要质量检查（关键信息覆盖率 ≥95%）

### 兼容性风险
- **风险**：skill 拆分可能影响现有流程
- **缓解**：保持向后兼容 + 完整测试
- **监控**：回归测试覆盖所有 action

### 复杂度风险
- **风险**：改动范围大，测试不充分
- **缓解**：分阶段实施 + 回归测试
- **监控**：每个阶段完成后执行完整测试

### 状态文件风险
- **风险**：状态文件格式错误或内容损坏
- **缓解**：文件格式校验（JSON Schema）+ 定期备份 + 写入时原子操作
- **监控**：状态文件完整性检查

## Migration Plan

### 阶段 1：懒加载（2-3 人天）
1. 拆分 sdd-brainstorm（472行 → 3个模块）
2. 拆分其他大型 skill（sdd-plan, sdd-code 等）
3. 实现懒加载机制（按需加载逻辑）
4. 测试验证（功能测试 + 回归测试）

### 阶段 2：上下文压缩（3-4 人天）
1. 设计摘要算法（关键信息提取逻辑）
2. 实现 artifact 摘要（spec、task、design 摘要）
3. 实现 review 压缩（diff + spec 场景传递）
4. 实现状态文件（轻量级状态格式）
5. 测试验证（精度验证 + 边界测试）

### 阶段 3：精度验证（2-3 人天）
1. 准备测试变更（3 个典型变更）
2. 执行优化前基线（记录基线数据）
3. 执行优化后对比（记录对比数据）
4. 人工审核（输出质量审核）
5. 调优和修复（根据验证结果调整）

### 回滚策略
- 分阶段回滚：懒加载回滚 → 上下文压缩回滚 → 全量回滚
- 回滚触发条件：任一指标低于回滚阈值、精度验证发现关键问题、用户反馈质量下降
