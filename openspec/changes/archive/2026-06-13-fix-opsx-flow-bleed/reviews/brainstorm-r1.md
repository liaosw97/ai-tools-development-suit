# Brainstorm Review — Round 1

**审查对象:** brainstorm.md
**日期:** 2026-06-11

## 总结

brainstorm 对问题的描述清晰准确，方案探索覆盖了从"不修改外部依赖"到"修改外部依赖"的完整谱系，决策结构规范。但存在以下主要不足：(1) 缺少明确的验收标准，无法判断问题是否被解决；(2) 对"不能修改 OPSX"这一核心约束的来源未做说明；(3) 方案 A 和方案 C 的区别不够清晰，决策 2 的理由不充分；(4) 功能拆分中的"L3: 用户教育层"存在过度设计倾向。

## Issues

### [major] 缺少验收标准
- **位置:** brainstorm.md 全文
- **描述:** brainstorm 没有定义"问题被解决"的验收标准。如何判断方案 C+E 实施后，用户不再跟随 OPSX 建议？没有量化指标或可观察的行为变化。
- **建议:** 在 brainstorm 中增加"验收标准"章节，例如：
  - 用户执行 SDD action 后，不再误执行 OPSX 命令
  - 用户反馈中不再出现"流程混乱"相关问题
  - 可通过观察用户会话日志验证

### [major] 核心约束来源不明
- **位置:** brainstorm.md §约束识别 → 技术约束
- **描述:** "不能修改 OPSX 命令文件（外部依赖）"被列为技术约束，但未说明来源。这是架构设计原则？团队约定？还是技术限制？如果不修改 OPSX 是硬约束，方案 B 和 D 的讨论就没有意义；如果是软约束，决策 1 的理由需要调整。
- **建议:** 明确约束来源，例如：
  - 如果是架构原则："OPSX 作为独立工具，其命令文件由独立团队维护，SDD 不应修改"
  - 如果是技术限制："OPSX 命令文件位于子模块，修改需要 upstream 合并"

### [major] 方案 A 与方案 C 区别模糊
- **位置:** brainstorm.md §方案探索
- **描述:** 方案 A（增强 SDD 后置逻辑覆盖）和方案 C（SDD 后置逻辑拦截并替换输出）在实现方式上非常相似，区别仅在于"覆盖"vs"拦截并替换"。决策 2 选择方案 C 而非 A，但理由不充分。
- **建议:** 明确两个方案的核心差异，例如：
  - 方案 A：SDD 后置逻辑在 OPSX 输出之后追加自己的建议（叠加）
  - 方案 C：SDD 后置逻辑明确警告用户忽略 OPSX 建议（覆盖+警告）
  - 决策 2 应说明为什么"警告"比"叠加"更好

### [minor] 功能拆分 L3 可能过度设计
- **位置:** brainstorm.md §功能拆分 → L3
- **描述:** L3 用户教育层包含"CLAUDE.md 更新"、"README.md 更新"、"示例说明"三项。其中"示例说明"的内容和位置不明确，且与前两项有重叠。
- **建议:** 合并为"L3: 文档更新"，明确具体要更新哪些文档的哪些章节，删除"示例说明"或说明其具体内容。

### [minor] 缺少回滚/恢复方案
- **位置:** brainstorm.md 全文
- **描述:** brainstorm 没有讨论如果用户已经误执行了 OPSX 命令（如 `/opsx:apply`），如何恢复到 SDD 流程。
- **建议:** 在 brainstorm 中增加"误操作恢复"章节，说明：
  - 用户执行 `/opsx:apply` 后，SDD 流程是否还能继续？
  - 如果能继续，如何继续？
  - 如果不能继续，如何回滚？

### [minor] 方案 E 的"长期"时间线不明确
- **位置:** brainstorm.md §推荐方案 → 长期
- **描述:** 方案 E 被标记为"长期"，但没有明确的时间节点或触发条件。什么是"长期"？一周后？一个月后？还是在某个版本发布时？
- **建议:** 明确长期方案的触发条件，例如：
  - "在 v0.4.0 版本发布前完成"
  - "在收集到 3 个以上用户反馈后启动"
