# Brainstorm: 修复 OPSX 命令导致的流程泄露问题

## 需求描述

当用户使用 ai-tools-bridge 的 SDD 流程（如 `/sdd-propose`、`/sdd-continue`、`/sdd-ff`）时，这些 action 会内部调用 OPSX 命令。问题是 OPSX 命令执行完成后会输出自己的"下一步建议"（如 `Run /opsx:apply to start implementing`），导致用户可能跟随 OPSX 的建议走 openspec 的流程，而不是继续走 SDD 的流程。

**具体场景**：
1. 用户执行 `/sdd-propose`
2. SDD 内部调用 `/opsx:propose`
3. `/opsx:propose` 完成后输出：`Run /opsx:apply to start implementing`
4. 用户看到建议后直接执行 `/opsx:apply`，跳过了 SDD 的后续流程（sdd-ff → sdd-plan → sdd-code）

## 方案探索

### 方案 A：增强 SDD 后置逻辑覆盖

**思路**：在 SDD action 的后置逻辑中，添加统一的"下一步建议"，利用后置逻辑的输出位置优势（最后显示）覆盖 OPSX 的建议。

**实现方式**：
- SDD action 执行完 OPSX 命令后，由 SDD 的后置逻辑输出统一的"下一步建议"
- 后置逻辑的输出会覆盖 OPSX 的建议（因为后置逻辑在最后执行）
- **不添加警告信息**，仅依赖输出顺序

**优点**：
- 不需要修改 OPSX 命令文件
- SDD 保持对流程的完全控制
- 符合现有的"薄编排"理念
- 用户体验干净，无冲突信息

**缺点**：
- 依赖 AI 行为的一致性（AI 必须遵循后置逻辑的指引）
- 如果 AI 输出顺序不稳定，OPSX 建议可能仍然显示在最后

**与方案 C 的区别**：
- 方案 A：纯依赖输出顺序，不添加警告
- 方案 C：添加明确的警告信息，告知用户忽略 OPSX 建议

---

### 方案 B：修改 OPSX 命令添加条件判断

**思路**：修改 OPSX 命令文件，使其能够检测自己是否被 SDD 调用，并相应调整输出。

**实现方式**：
- 在 OPSX 命令中添加环境变量检测（如 `SDD_CONTEXT=true`）
- 如果检测到 SDD 上下文，跳过"下一步建议"输出
- 或者输出通用建议：`请继续执行 SDD 流程的下一步`

**优点**：
- 从根本上解决问题
- OPSX 命令能够自适应不同的调用场景

**缺点**：
- 需要修改 OPSX 命令文件（外部依赖）
- 增加了 OPSX 命令的复杂度
- 需要协调两个项目的改动

---

### 方案 C：SDD 后置逻辑拦截并替换输出

**思路**：SDD 后置逻辑在 OPSX 命令执行后，明确输出覆盖信息，并添加警告标识。

**实现方式**：
```markdown
### 完成引导

sdd-propose 完成。

产物已持久化至:
  openspec/changes/<name>/proposal.md

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
SDD 流程指引（请忽略上方可能显示的 OPSX 建议）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

推荐下一步:
  1. ★ /sdd-ff — 快进生成所有文档
  2. ○ /sdd-continue — 逐步确认细节
```

**优点**：
- 实现简单
- 不依赖外部项目修改
- 明确告知用户不要跟随 OPSX 建议
- 即使 OPSX 建议显示在最后，用户也能看到警告

**缺点**：
- 用户体验不够优雅（有冲突信息）
- 可能让用户困惑为什么会有冲突的建议

**与方案 A 的区别**：
- 方案 A：纯依赖输出顺序，不添加警告，用户体验更干净但风险更高
- 方案 C：添加明确警告，即使输出顺序不稳定也能引导用户，但有冲突信息

---

### 方案 D：创建 SDD 包装器隔离 OPSX 输出

**思路**：创建一个包装层，调用 OPSX 命令但捕获其输出，只显示 SDD 的输出。

**实现方式**：
- 创建 SDD 自有的 OPSX 调用函数
- 该函数调用 OPSX 命令但过滤掉"下一步建议"部分
- SDD 后置逻辑使用过滤后的输出

**优点**：
- 完全隔离 OPSX 的输出
- 用户体验干净

**缺点**：
- 实现复杂
- 需要解析 OPSX 的输出格式
- 维护成本高

---

### 方案 E：文档约定 + 后置逻辑增强

**思路**：通过文档明确说明 SDD 流程的独立性，并在后置逻辑中强化 SDD 的引导。

**实现方式**：
1. 在 CLAUDE.md 和 README.md 中明确说明：
   - SDD 流程是独立的编排层
   - OPSX 命令的建议仅在独立使用 OPSX 时有效
   - 使用 SDD 流程时应忽略 OPSX 的建议

2. 在 SDD 后置逻辑中：
   - 明确列出 SDD 的下一步操作
   - 使用醒目的格式（如 ★○△ 标记）
   - 添加提示："以下为 SDD 流程的推荐步骤"

**优点**：
- 不需要代码修改
- 通过教育用户解决问题
- 符合"薄编排"理念

**缺点**：
- 依赖用户阅读文档
- 不能从根本上解决问题

---

## 关键决策

### 决策 1：是否修改 OPSX 命令？

**选择 [A/C/E] 而非 [B/D]**：保持 OPSX 命令的独立性，不修改外部依赖。

**理由**：
- OPSX 是独立的工具，应该保持其完整性
- 修改 OPSX 会增加协调成本和维护负担
- SDD 作为编排层应该承担流程控制的责任

### 决策 2：采用哪种覆盖策略？

**选择 [方案 C + E 组合]**：
1. 在 SDD 后置逻辑中明确输出 SDD 的下一步建议（方案 C）
2. 在文档中说明 SDD 流程的独立性（方案 E）
3. 使用醒目的格式区分 SDD 建议和可能的 OPSX 建议

**理由**：
- 实现简单，不需要修改外部依赖
- 通过后置逻辑的输出位置优势（最后显示）覆盖 OPSX 建议
- 文档补充提供长期的用户教育

### 决策 3：覆盖信息的格式设计

**选择醒目的警告格式**：
```markdown
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
SDD 流程指引（请忽略上方可能显示的 OPSX 建议）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

推荐下一步:
  1. ★ /sdd-ff — 快进生成所有文档
  2. ○ /sdd-continue — 逐步确认细节
```

**理由**：
- 视觉上与 OPSX 建议明显区分
- 明确告知用户忽略 OPSX 建议
- 保持 SDD 流程的连贯性

## 验收标准

**问题解决的量化指标**：
1. **主流程无泄露**：执行 `/sdd-propose` → `/sdd-ff` → `/sdd-code` 完整流程时，用户不会看到引导至 `/opsx:apply` 的建议
2. **SDD 引导可见**：每个 SDD action 完成后，SDD 的下一步建议必须在输出中最后显示
3. **误操作可恢复**：用户误执行 OPSX 命令后，能够通过 `/sdd-continue` 回到 SDD 流程

**可观察行为变化**：
- 修复前：`/sdd-propose` 完成后显示 `Run /opsx:apply to start implementing`
- 修复后：`/sdd-propose` 完成后显示 `★ /sdd-ff — 快进生成所有文档`

## 约束识别

### 约束 1：不能修改 OPSX 命令文件

**约束来源**：架构原则（非技术限制）

**原因**：
- OPSX 和 ai-tools-bridge 是两个独立的项目/插件
- SDD 的核心理念是"薄编排"——只做编排，不修改底层工具
- 修改 OPSX 会破坏项目的独立性，增加维护耦合
- 用户可能单独使用 OPSX（不通过 SDD），修改会影响独立使用场景

**影响**：
- 排除方案 B（修改 OPSX 添加条件判断）
- 排除方案 D（创建 SDD 包装器隔离 OPSX 输出，因需要深度集成）

### 约束 2：SDD 后置逻辑执行顺序

**约束来源**：技术实现

**原因**：
- Claude Code 的 skill 执行模型中，invoke 的底层 skill 输出会先显示
- SDD 的后置逻辑在底层 skill 完成后执行
- 因此后置逻辑的输出会出现在 OPSX 建议之后

### 约束 3：用户体验约束

- 不能让用户感到困惑
- 需要清晰的引导，避免歧义
- 保持 SDD 流程的简洁性

## 误操作恢复方案

**场景**：用户误执行了 OPSX 命令（如 `/opsx:apply`），跳过了 SDD 流程。

**恢复路径**：
1. **检测当前状态**：执行 `/sdd-doctor` 检查当前变更的状态
2. **回到 SDD 流程**：执行 `/sdd-continue` 或 `/sdd-ff` 继续 SDD 流程
3. **状态兼容性**：OPSX 命令生成的 artifact 与 SDD 兼容（都使用 openspec/changes/<name>/ 目录）

**注意事项**：
- OPSX 的 artifact 格式可能与 SDD 模板略有差异
- 恢复后可能需要执行 `/sdd-review-spec` 检查 artifact 质量
- 在 CLAUDE.md 中添加恢复指南
