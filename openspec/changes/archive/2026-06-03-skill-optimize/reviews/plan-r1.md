# Plan Review — Round 1

**审查对象:** plan.md
**日期:** 2026-06-01

## 总结

plan.md 结构清晰，任务覆盖完整（27 个任务与 tasks.md 一致），批次划分合理。但 TDD 步骤存在形式化问题：RED/GREEN 步骤主要是文件存在性检查而非功能验证，验证命令不够充分，缺少依赖关系标记和风险识别。

## Issues

### [severity: major] TDD 步骤形式化
- **位置:** plan.md 全局（Task 1.1-4.4）
- **描述:** RED 步骤仅验证文件是否存在（`ls ... && echo "EXISTS"`），GREEN 步骤仅创建/修改文件。这不是真正的 TDD——真正的 RED 应该是"验证功能不工作"，GREEN 应该是"实现功能使其通过"。
- **建议:** 对于共享模块提取任务，RED 应验证"SKILL.md 中不包含 include 引用"，GREEN 应验证"改造后 SKILL.md 包含正确的 include 引用且行数减少"。

### [severity: major] 验证命令不充分
- **位置:** plan.md Task 1.2-1.6、Task 2.1-4.4
- **描述:** 验证命令只检查文件存在性和行数，不检查内容正确性。例如 Task 1.2 的验证只检查文件是否存在，不验证 base-triggers.md 是否包含模板内容。
- **建议:** 增加内容验证命令，例如 `grep -c "触发" ai-tools-bridge/skills/_shared/base-triggers.md` 验证模板内容存在。

### [severity: major] 缺少依赖关系标记
- **位置:** plan.md 全局
- **描述:** plan.md 没有明确标记任务间的依赖关系。批次二、三、四的改造任务都依赖批次一的共享模块创建，但未标记。批次二、三、四之间无依赖，可并行执行，但未说明。
- **建议:** 在每个任务前添加依赖标记，例如 `[depends: Task 1.1-1.6]`，并说明哪些任务可并行。

### [severity: minor] Task 1.1 粒度过小
- **位置:** plan.md §Task 1.1
- **描述:** Task 1.1 只是创建目录（`mkdir -p`），不到 1 分钟即可完成，粒度过小。
- **建议:** 将 Task 1.1 与 Task 1.2 合并，或将其标记为前置步骤而非独立任务。

### [severity: minor] 缺少风险标记
- **位置:** plan.md 全局
- **描述:** include 机制是纯约定（HTML 注释），没有实际代码支持。如果 AI 不识别 include 语法，SKILL.md 将无法正常工作。plan.md 没有标记这个高风险点，也没有回滚方案。
- **建议:** 在批次五验证阶段增加 include 机制实际工作验证，并说明如果 include 不工作时的回滚方案（恢复原始 SKILL.md）。

### [severity: minor] Task 5.1 验证逻辑不清
- **位置:** plan.md §Task 5.1
- **描述:** Task 5.1 的 RED 步骤是"运行测试，预期失败"，但未说明预期什么类型的失败。GREEN 步骤是"修复任何测试失败"，但未说明如何修复。
- **建议:** 明确预期的测试失败类型（例如 schema 验证失败），并说明修复方法。

### [severity: minor] 缺少并行执行说明
- **位置:** plan.md 批次二、三、四
- **描述:** 批次二、三、四的改造任务之间无依赖，可并行执行以提高效率，但 plan.md 未说明。
- **建议:** 添加说明："批次二、三、四的改造任务可并行执行，共享模块创建完成后即可开始"。

## 结论

NEEDS_REVISION

plan.md 需要修订以下内容：
1. 修正 TDD 步骤，使其真正反映测试驱动开发（RED = 验证功能不工作，GREEN = 实现功能使其通过）
2. 增强验证命令，添加内容正确性检查
3. 标记任务依赖关系，说明可并行执行的任务
4. 标记高风险步骤（include 机制）和回滚方案
5. 合并或重新定义粒度过小的任务（Task 1.1）
