# Brainstorm Review — Round 1

**审查对象:** brainstorm.md
**日期:** 2026-06-01

## 总结

brainstorm.md 整体质量良好，需求描述清晰，方案探索全面，关键决策有明确的结论和理由。文档识别了主要的重复内容（触发条件、输出约束、角色加载等），提出了 3 个可行方案并进行了合理比较。决策部分结构规范，每个决策都有选择、理由和被否决的替代方案。但存在几个需要改进的地方：缺少"功能完整性"的量化验证标准、未考虑部分低频共享模块的 ROI、以及边界条件处理不够明确。

## Issues

### [severity: major] 缺少"功能完整性"的量化验证标准
- **位置:** brainstorm.md §关键决策 - 决策 2、决策 3
- **描述:** 决策 2 要求"保持所有细节不变"，决策 3 提到"双轨验证"，但都没有定义如何量化验证"功能完整性"。diff 审查只能发现结构变化，无法自动验证语义等价性。
- **建议:** 增加明确的验证标准，例如：
  - 定义"功能完整性"的检查清单（触发条件、输出格式、错误处理、示例等）
  - 指定 diff 审查的具体关注点（不能只看行数变化）
  - 考虑增加"语义验证"步骤：逐条对比原始 SKILL.md 中的每条指令是否在新版本中保留

### [severity: major] 未定义边界条件和异常处理
- **位置:** brainstorm.md §方案探索 - 方案 A
- **描述:** 方案 A 假设所有重复内容都可以提取到共享模块，但没有考虑边界情况：
  - 如果某个 SKILL.md 的触发条件有特殊变体怎么办？
  - 如果某个 SKILL.md 需要覆盖共享模块的默认行为怎么办？
  - include 机制解析失败时如何处理？
- **建议:** 增加"边界条件"章节，明确：
  - 共享模块支持覆盖/扩展的机制
  - include 解析失败的降级策略
  - 不适合提取到共享模块的内容类型

### [severity: minor] breakdown-mode 和 review-loop 引用次数较低
- **位置:** brainstorm.md §方案探索 - 方案 A - 共享模块
- **描述:** breakdown-mode（2 次引用）和 review-loop（5 次引用）的引用次数相对较低，提取为独立共享模块的 ROI 需要评估。如果这两个模块本身行数不多，提取可能增加复杂度而非减少。
- **建议:** 补充这两个模块的原始行数数据，计算提取前后的净节省量。如果净节省不明显，考虑合并为一个"advanced-patterns.md"或保留在各自的 SKILL.md 中。

### [severity: minor] 缺少性能约束识别
- **位置:** brainstorm.md §约束识别
- **描述:** 约束识别中未提及 include 机制的性能影响。每次加载 SKILL.md 时需要解析 include 指令并读取多个文件，这可能增加加载延迟。
- **建议:** 增加性能约束：是否需要缓存共享模块？include 解析的预期延迟是多少？是否需要在构建时预处理而非运行时解析？

### [severity: minor] 功能拆分缺少验收标准
- **位置:** brainstorm.md §功能拆分
- **描述:** L1/L2/L3 的拆分清晰，但每个层级缺少明确的验收标准（Definition of Done）。"验证 frontmatter 不变"是 L2 的唯一标准，过于单薄。
- **建议:** 为每个层级增加验收标准：
  - L1：5 个共享模块创建完成，每个模块有独立的单元测试
  - L2：每个 SKILL.md 改造后通过 diff 审查 + 结构验证
  - L3：全量测试通过，生成 token 节省报告

### [severity: minor] 未说明 include 机制的兼容性验证方式
- **位置:** brainstorm.md §约束识别 - 技术约束
- **描述:** 提到"include 机制需兼容现有的文件读取方式"，但没有说明如何验证兼容性。Claude Code 插件如何解析 SKILL.md？是否支持 HTML 注释语法？
- **建议:** 明确：
  - Claude Code 插件加载 SKILL.md 的具体机制
  - `<!-- include: path -->` 语法是否会被插件忽略或特殊处理
  - 是否需要修改插件代码以支持 include，还是纯约定（AI 自行解析）
