# Brainstorm Review — Round 1

**审查对象:** brainstorm.md
**日期:** 2026-05-12

## 总结

brainstorm.md 整体质量较高。需求描述清晰，痛点可追溯；方案探索覆盖了三个可行方向，选定了合理的渐进增强策略（方案 A）；6 个关键决策均包含选择、理由和被否决的替代；设计详情具体到流程、委托关系和文件级别；约束识别到位。主要问题集中在：方案对"自动触发不准确"这一痛点缺少直接、针对性的技术方案；`sdd-quick` 的适用边界和失败回退路径未明确；推荐操作映射表与变更清单之间存在轻微不一致；复杂度评估的阈值缺少推导依据。

## Issues

### [severity: major] 痛点 3（自动触发不准确）缺少直接解决方案
- **位置:** brainstorm.md §方案探索 + §关键决策 + §设计详情
- **描述:** 需求描述了 4 个痛点，但方案 A 的 6 项变更中，没有一项直接针对"自动触发不准确"提出技术方案。决策 5（智能分级触发）仅说明保留自动触发并增加复杂度判断，但这解决的是"走哪条路径"，而非"触发后生成的文档为何不准确"。§4（修改 sdd-doctor 复杂度评估）和§5（统一推荐操作机制）通过引导用户选择正确路径间接缓解了该问题，但并未触及自动触发本身的准确性根因。在§方案比较中也未解释方案 A 如何具体解决此痛点。
- **建议:** 补充对"自动触发不准确"根因的简要分析（例如：上下文不足、触发条件过于宽泛、缺少前置校验等），并明确本次是通过"推荐操作引导 + 复杂度分级"间接缓解，还是需要针对触发逻辑本身做修改。如果是间接缓解，应在变更清单中标注该痛点为"部分解决"。

### [severity: major] sdd-quick 缺少适用边界和回退机制
- **位置:** brainstorm.md §设计详情 §1. 新增 Action: /sdd-quick
- **描述:** `/sdd-quick` 设计为快速模式，流程中硬编码了上限（5 个苏格拉底式问题、5 个场景、10 个任务）。但缺少以下关键说明：(1) 当需求在 quick 流程中超出这些上限时，如何处理？是自动回退到标准路径，还是报错中断？(2) 用户如何判断一个需求是否适合 quick 模式？目前仅在 sdd-doctor 的路径推荐中按复杂度分级，但 quick 本身的 SKILL.md 入口缺少前置校验描述。(3) quick 生成的 spec/tasks 质量如何保障？省略了 plan.md 和 review 环节，是否会降低交付质量？
- **建议:** 在§1 中补充：(a) 超限处理策略（建议：检测到超限时输出提示，推荐切换到 `/sdd-propose` 开始标准路径，已有的中间产物可复用）；(b) 在 SKILL.md 设计中增加前置自检步骤；(c) 明确 quick 模式的质量折中说明——适用于低风险变更，复杂需求不应使用。

### [severity: minor] 推荐操作映射表与变更清单不完全对齐
- **位置:** brainstorm.md §设计详情 §5. 统一推荐操作机制
- **描述:** 映射表中 `sdd-review-code` 完成后的★推荐为 `/sdd-test-code`，这是合理的。但表中未列出 `sdd-review-spec` 完成后的○可选操作是否包含 `/sdd-test-code`，而 `sdd-test-code` 作为新增 action，其与现有 review-spec 流程的衔接关系不够清晰。另外，表中 `sdd-doctor` 的推荐写为"按复杂度推荐"，但§4 中复杂度评估仅给出 S/M/L 三级对应路径，未说明 doctor 的推荐输出格式是否与统一的★○△格式一致。
- **建议:** 确认 `sdd-doctor` 的推荐输出也遵循★○△格式，并在映射表中用具体推荐替代"按复杂度推荐"的占位描述。补充 `sdd-test-code` 在整体流程图中与 review-spec 的关系。

### [severity: minor] 复杂度评估阈值缺少推导依据
- **位置:** brainstorm.md §设计详情 §4. 修改 Action: /sdd-doctor 复杂度评估
- **描述:** 复杂度评级（简单 S：1-3 场景 / ≤5 任务 / 单领域；中等 M：4-8 / 6-15 / 1-2 领域；复杂 L：>8 / >15 / 3+ 领域）以及 5 个指标的权重分配（高/中/低）均为经验性数值，但 brainstorm 中未说明这些阈值的推导依据或参考来源。这可能导致后续实施时因阈值不合适而需要反复调整。
- **建议:** 补充一段说明，标明阈值为初始经验值，计划在 v0.3.0 发布后根据实际使用反馈迭代调整。或者在 proposal/spec 阶段将阈值定义为可配置参数。

### [severity: minor] Skills 内联的许可证/合规性未提及
- **位置:** brainstorm.md §关键决策 §决策 1 + §设计详情 §6. Skills 内联范围
- **描述:** 决策 1 选择直接内联 skills 内容为 reference-*.md 文件，并在 README 中标注来源。但未提及 skills 子模块的具体开源许可证类型，以及内联后是否符合其许可要求（如署名方式、是否需要保留 LICENSE 文件等）。
- **建议:** 补充一句说明 skills 子模块的许可证类型以及内联后的合规措施（例如在 reference 文件头部保留原始 LICENSE 声明）。如果 skills 为同一作者/组织的项目，可简要说明"同一项目体系内，无许可证冲突"即可。
