# Plan Review — Round 1

**审查对象:** plan.md
**日期:** 2026-05-12

## 总结

plan.md 将 tasks.md 的 45 个任务组织为 6 个批次，按依赖关系从基础设施到上层功能逐步推进。每个任务均包含 RED/GREEN 两步 TDD 流程和验证命令。整体结构清晰，任务-规格链接完整。但存在几个需要关注的问题：批次 1 任务数偏多（10 个），部分任务粒度过细可能在实际执行中与上下任务合并，批次 5 将 sdd-doctor（功能增强）和前置校验（横切关注点）混在同一批次增加了认知负担。

## Issues

### [severity: major] 批次 1 任务数超出建议上限
- **位置:** plan.md 批次 1/6
- **描述:** 批次 1 包含 Task 7.1、7.2、1.1-1.6 共 8 个任务（注释声明覆盖 7.1, 7.2, 1.1-1.6 = 8 个），但 plan 标题标注"基础设施 + sdd-quick 核心"范围合理却略超每批 5-10 任务的上限。实际为 8 个任务，在范围内，但 8 个任务中多个是对同一文件 SKILL.md 的连续修改（1.1-1.6），执行时每个任务的 RED 步骤需要反复运行 `pnpm test`，实际耗时可能偏长。
- **建议:** 可接受，但建议在执行时将 1.2-1.6 的 RED 测试合并编写一次，再逐步 GREEN。plan 层面无需调整。

### [severity: minor] Task 1.1 与 1.2 粒度过细
- **位置:** plan.md 批次 1 Task 1.1 + Task 1.2
- **描述:** Task 1.1 创建含 YAML 前置元数据的 SKILL.md 骨架，Task 1.2 编写完整内容。两步合计预估 3-4 分钟，合并为一个任务更符合 2-5 分钟粒度。拆成两步后 Task 1.1 的 GREEN（仅创建含 YAML 占位的空文件）几乎无实质意义——实际执行时 1.1 通过后立即做 1.2，中间无 checkpoint 价值。
- **建议:** 合并为单个任务"创建 sdd-quick SKILL.md 完整内容"，RED 步骤合并验证骨架 + 三段结构。

### [severity: minor] Task 2.1 与 2.2 粒度过细
- **位置:** plan.md 批次 3 Task 2.1 + Task 2.2
- **描述:** 与 1.1/1.2 同样的问题——2.1 创建骨架，2.2 编写完整内容。对于 Markdown 文件创建，骨架 + 完整内容写入手动操作上是一体的。
- **建议:** 同上合并。

### [severity: minor] 同一文件的多次连续修改缺乏合并策略
- **位置:** plan.md 批次 1 Task 1.3-1.6（sdd-quick/SKILL.md）、批次 3 Task 2.3-2.7（sdd-test-code/SKILL.md）、批次 4 Task 3.1-3.8（sdd-plan/SKILL.md）
- **描述:** 多个任务对同一文件做增量修改，每个任务都有独立的 RED/GREEN 循环。对于 Markdown skill 文件，"编写测试验证包含某段文字" 然后 "在该文件中加入该段文字" 的模式，每步实际耗时 < 2 分钟，导致粒度偏细。同时每步都需要 `pnpm test` 运行全套测试，而非仅运行相关测试文件。
- **建议:** 在 plan 中增加注释提示执行者可将同一文件的连续修改合并为一个 RED/GREEN 循环。或保持现有粒度但在执行指引中说明允许合并。

### [severity: major] 批次 5 混合了两个独立关注点
- **位置:** plan.md 批次 5/6
- **描述:** 批次 5 包含 Task 4.1-4.7（sdd-doctor 复杂度评估）和 Task 5.1-5.8（所有 action 前置校验），共 15 个任务。注释声明 `任务范围：4.1-4.7, 5.1-5.8`。15 个任务远超每批 5-10 任务的建议上限。且 sdd-doctor 的功能增强和前置校验的横切修改是两个独立关注点，混在一起增加 review 和 checkpoint 的认知负担。
- **建议:** 拆分为两个批次：(A) sdd-doctor 复杂度评估（4.1-4.7，7 个任务）；(B) 前置校验（5.1-5.8，8 个任务）。这样总批次变为 7 个，每批任务数更均匀。

### [severity: major] 批次 5 共 15 个任务超出上限
- **位置:** plan.md 批次 5/6
- **描述:** 批次 5 包含 Task 4.1-4.7（7 个）和 Task 5.1-5.8（8 个），合计 15 个任务，显著超过"每批 5-10 任务"的约束。虽然这些任务的个体粒度较细（每个 < 2 分钟），但 15 个任务的上下文切换成本较高。
- **建议:** 同上，拆分为两个独立批次。

### [severity: minor] 批次间依赖关系未显式标注
- **位置:** plan.md 全文
- **描述:** 6 个批次通过 `--- checkpoint ---` 分隔，但未显式说明批次间的依赖关系。例如批次 3（sdd-test-code）依赖批次 1 中的 schema 注册（Task 7.1），但这一点没有用文字说明。读者需要从任务编号和 spec 链接推断依赖。
- **建议:** 在每个批次标题后增加一行简短依赖说明，如"依赖：批次 1 完成"。

### [severity: minor] 验证命令缺少针对性
- **位置:** plan.md 全文所有任务
- **描述:** 所有任务的验证命令统一为 `cd ai-tools-bridge && pnpm test`，运行全套测试。对于单个任务的 RED 阶段，理想情况是仅运行与该任务相关的测试文件以加速反馈循环。但在纯 Markdown 项目中，测试套件本身可能较小，全量运行耗时可控。
- **建议:** 可接受。若测试套件增长，后续可考虑在 RED 步骤中指定测试文件路径。

### [severity: minor] Task 3.7 和 3.8 的 spec 链接不精确
- **位置:** plan.md 批次 4 Task 3.7、Task 3.8
- **描述:** Task 3.7 链接 `[spec:pre-validation#sdd-ff 阻断 — proposal 不存在]`，但实际是 sdd-plan 的前置校验（检查 tasks.md + spec 存在性），与 sdd-ff 的阻断场景不完全匹配。Task 3.8 链接 `[spec:recommendation#sdd-code 完成后输出 ★○△ 推荐操作]`，但实际是 sdd-plan 的后置推荐。spec 链接指向了相关但不精确的场景。
- **建议:** 确认 spec 中是否有 sdd-plan 对应的前置校验和后置推荐场景。如果有，更新链接；如果没有，保留现有链接但在描述中注明是相关场景。

## 结论

**NEEDS_REVISION**

主要问题：批次 5 任务数（15 个）超出每批 5-10 任务的上限，且混合了两个独立关注点，建议拆分为两个批次。次要问题：部分任务粒度偏细（同一文件的连续小修改），在执行层面可通过合并 RED 步骤解决，plan 结构层面可作为改进但非阻塞项。其余维度（TDD 完整性、Spec 对齐、验证命令）表现良好。
